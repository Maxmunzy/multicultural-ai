# SchoolBridge 최신 발표정리

> 작성일: 2026-05-08 | 발표/PPT 재료용 | 코드·폴더 수정 없음

---

## 1. 프로젝트 개요

- **프로젝트명**: SchoolBridge
- **목적**: 다문화 학부모가 가정통신문을 듣고 이해하고 행동할 수 있도록 지원
- **주 사용자**: 한국어 가정통신문 이해에 어려움을 겪는 다문화 학부모
- **문제 정의**: 다문화 학부모는 한국어 중심 가정통신문을 번역해도, 신청기한·제출물·준비물·학교문화 맥락을 놓칠 수 있으므로, 이를 듣고 이해하고 행동할 수 있게 돕는 음성 접근성 기반 학교 소통 서비스가 필요합니다.
- **서비스 한 줄 설명**: SchoolBridge는 가정통신문을 체크리스트, 준비물 설명, 문화 접근성 카드, TTS 음성 안내로 재구성하는 학교 소통 음성 접근성 AI 도우미입니다.

---

## 2. 사용자와 Pain Point

### 대상 사용자

- 한국어 읽기 이해가 아직 충분하지 않은 다문화 학부모
- 가정통신문을 읽어도 무엇을 해야 하는지 놓치기 쉬운 보호자
- 한국 학교문화와 기념일 맥락이 익숙하지 않은 학부모

### Pain Point

- 긴 가정통신문에서 해야 할 일을 찾기 어려움
- 날짜·신청기간·운영일시·제출기한을 놓치기 쉬움
- 도화지, 크레파스, 리코더, 클리어 화일 같은 준비물은 번역해도 실제 물건을 모를 수 있음
- 한글날, 재량휴업일, 현장체험학습 같은 한국 학교문화 맥락은 이해하기 어려움
- 단순 번역앱은 문장 번역은 해주지만 행동 관리까지는 하지 않음

## 3. 기존 방식의 한계

### 비교 대상: 일반 번역앱 / GPT·Gemini / 문서 전체 TTS

| 기존 방식 | 한계 |
|---|---|
| 일반 번역앱 | 번역은 가능하지만 체크리스트 상태 추적 없음 |
| GPT / Gemini | 설명·번역은 가능하지만 학부모 완료 상태를 지속 관리하지 않음 |
| 문서 전체 TTS | 너무 길고, 핵심 행동 정보가 묻힘 |
| 모든 번역 방식 공통 | 날짜·시간·URL·전화번호가 번역 과정에서 왜곡될 수 있음 |
| 모든 번역 방식 공통 | 준비물은 번역만으로 실제 물건 이해가 어려울 수 있음 |
| 모든 번역 방식 공통 | 한국 학교문화 맥락은 단어 번역만으로 부족함 |

## 4. 서비스 목표

| 질문 | SchoolBridge 대응 |
|---|---|
| 무엇을 해야 하는가 | 체크리스트 |
| 언제 해야 하는가 | 미니 달력 |
| 무엇을 준비해야 하는가 | 준비물 이미지·설명 |
| 왜 쉬는가 / 무슨 의미인가 | 문화 접근성 카드 |
| 어떻게 들을 수 있는가 | TTS 음성 안내 |

> **핵심 문장**: SchoolBridge는 가정통신문을 번역하는 앱이 아니라, 다문화 학부모가 듣고 이해하고 행동할 수 있게 돕는 음성 접근성 서비스입니다.

## 5. 전체 파이프라인

```
[입력]
PDF / HWP / 텍스트 업로드
        ↓
[문서 구조화]
문단 분리 → sentence_list 생성 (LLM 또는 rule-based fallback)
        ↓
[Model A: 해야 할 일 추출]
학부모 행동 문장 추출 (제출/신청/준비/납부/참석)
        ↓
[Model B: 카테고리·중요도 분류]
일정 / 준비물 / 제출 / 비용 / 건강·안전 / 기타 → chip + importance
        ↓
[Slot Preservation / info_cards]
날짜·시간·금액·URL·전화·대상·장소·신청기간·문의 보존
        ↓
[체크리스트 생성]
준비물 콤마 split → 개별 항목 / 제출·납부 → 단일 액션 항목
        ↓
[NLLB 번역 + 보호]
glossary injection / template-based / slot masking → 사실값 왜곡 방지
        ↓
[TTS 생성]
쉬운 한국어 + 모국어 음성 파일 생성
        ↓
[Android UI 출력]
체크리스트 / 준비물 이미지 / 미니 달력 / TTS 버튼
```

### 단계별 역할 요약

- **문서 구조화**: PDF·HWP 텍스트 추출 → 단락 단위 sentence_list 생성; LLM 검증 실패 시 rule-based fallback
- **Model A**: 행동 유발 문장 판별 (is_todo), 신뢰도(confidence) 점수 출력
- **Model B**: 카테고리 분류 + chip 태그 부여, 중요도 정렬
- **Slot Preservation**: 모델이 놓친 사실값(날짜·URL·금액 등)을 regex로 보완 → info_cards로 별도 표시
- **번역 모듈**: 핵심 용어는 glossary·template으로 보호, 나머지는 NLLB; 사실값은 번역 skip
- **TTS**: 행동 안내 콘텐츠 중심으로 생성 (전체 문서 낭독 아님)
- **Android**: 분석 결과 렌더링, 체크리스트 상태 관리, 준비물 이미지 표시, 달력 UI

## 6. 모델 및 모듈 역할

### Model A: 해야 할 일 추출

- **담당자**: 윤정
- **역할**: 가정통신문에서 학부모 행동 문장(제출/신청/준비/납부/참석) 추출
- **모델**: KoELECTRA-base-v3 discriminator 파인튜닝 (이진 분류: 할 일 / 노이즈)
- **입력**: 문단 문장 또는 sentence_list
- **출력**: action 후보 문장, is_todo 판별, confidence(확률값) → 임계값 기반 분류
- **HF Hub**: `yunjeong116/koelectra-extractor` (main: v4_merged / base-v1: v3.1.3)

#### 성능 지표 — galsan unseen 테스트셋 (5,388문장 / 할 일 712 · 노이즈 4,676)

| 모델 | Threshold | Accuracy | F1 (할 일) | Precision | Recall |
| --- | --- | --- | --- | --- | --- |
| base-v1 (v3.1.3 학습) | 0.60 | 72.03% | 0.4166 | 0.2875 | 0.7556 |
| base (v4_merged 재학습) | 0.70 | 74.00% | 0.4687 | 0.3210 | 0.8680 |
| **향상 폭** | | **+1.97%p** | **+0.0521** | **+0.0335** | **+0.1124** |

> **해석**: 클래스 불균형(할 일:노이즈 ≈ 1:6.6)으로 F1 절대값은 낮으나,
> 학부모가 해야 할 일을 놓치지 않는 것이 우선이므로 **Recall 중심으로 평가**.
> v4_merged 재학습 후 Recall +11.2%p 향상 — 더 많은 행동 문장을 포착.

### Model C / 번역·TTS (세종 파트)

#### 담당 범위

- NLLB 기반 다국어 번역 모듈 설계 및 안정화
- term_glossary.csv 구축 및 용어 주입 구조 설계
- template-based translation 설계 (준비물·제출 문장 NLLB 우회)
- slot 보호 구조 설계 (날짜·시간·금액·URL·전화번호 오역 방지)
- 준비물 이미지·쉬운 설명 기능 기획 및 Android 연결
- TTS 파일 생성 및 재생 연결
- 번역 파이프라인 전체를 팀 프로젝트 서비스에 통합·안정화
- vi_demo(시연용) 모드 설계: 발표자 UI는 한국어, 백엔드 번역은 베트남어

#### 문제 인식

- NLLB-200은 범용 다국어 모델로, 학교 안내문 도메인 데이터를 학습하지 않음
- "리코더" → 녹음기(recorder)로 오역, "클리어 화일" → 명확한 파일(clear file)로 의미 왜곡
- 날짜·금액·URL 같은 사실값이 번역 과정에서 임의로 변형되거나 누락될 수 있음
- 단순히 번역 API를 바꾸거나 프롬프트를 조정하는 것만으로는 도메인 용어 보존이 어려움
- 준비물 이름을 정확히 번역해도 다문화 학부모가 실제 물건을 알아보기 어려운 경우 있음

#### 실험 과정 (translation-tts-lab)

- 팀 레포 직접 적용 전, 개인 실험 레포(translation-tts-lab)에서 번역 실패 조건을 먼저 검증
- 실험 대상: 학교 준비물 명사 17종, 행동 지시 문장 20종
- 비교한 방식: 직접 치환 / prefix hint / slot masking / glossary + template 구조
- 실패 방식별 원인까지 기록해 팀 적용 기준 문서화

| 실험 방식 | 용어 보존 성능 | 실패 원인 및 판단 |
|---|---|---|
| 직접 치환 | 9/17, 53% | NLLB가 치환된 표현과 한국어 조사가 섞인 입력을 안정적으로 보존하지 못함 |
| prefix hint | 1/17, 6% | NLLB가 hint를 번역 지시가 아닌 번역 대상 텍스트처럼 처리하는 경향 |
| slot masking | 0/17, 0% | 준비물 명사를 마스킹하면 문맥이 부족해져 출력이 불안정 |
| glossary + template 구조 | 8문장 17/17 / 20문장 37/37 | 준비물 중심 샘플에서 핵심 용어 보존을 확인 |

#### 적용한 개선 구조

- **slot protection**: 날짜·금액·URL·전화번호를 `__SLOT0__` 토큰으로 치환 후 번역, 번역 후 원문 복원 → 사실값 왜곡 방지
- **glossary injection**: 핵심 용어를 번역어로 slot 치환 → NLLB가 건드리지 못하게 한 뒤 복원 → 오역 방지
- **template-based translation**: 준비물·제출 문장(준비해 주세요/가져오세요 유형)은 NLLB 완전 우회 → 준비물 중심 샘플에서 핵심 용어 보존을 안정화 (제한된 테스트셋 기준)
- **LRU 캐시 + batch generate**: 동일 분석 내 반복 등장하는 헤더(준비물·비용 등) dedup → NLLB 1회 forward → 속도 약 17% 감소 (31s → 25s)
- **준비물 이미지·설명**: 번역 결과만으로 실물 이해가 어려운 10종 준비물에 대해 쉬운 설명 + 예시 이미지 제공 → 체크리스트 탭과 연결

> ※ 실험에서 실패한 slot masking은 준비물 명사 자체를 마스킹한 방식입니다. 현재 적용한 slot protection은 날짜·시간·URL·전화번호처럼 번역하면 안 되는 사실값을 보호하는 구조로, 적용 대상이 다릅니다.

#### 발표에서 말할 핵심 문장

- NLLB를 그대로 쓰면 학교 용어가 오역됩니다. 어떤 방식이 왜 실패하는지 실험하고, 모델이 건드리면 안 되는 부분과 번역할 수 있는 부분을 분리했습니다.
- 준비물 이름을 정확히 번역해도 실제 물건을 모를 수 있기 때문에, 이미지와 쉬운 설명을 체크리스트에 연결했습니다.
- 세종 파트의 목표는 번역을 예쁘게 만드는 것이 아니라, 학부모가 놓치면 안 되는 정보를 보존하고 TTS로 안내 가능한 구조로 만드는 것이었습니다.

### Backend (담당자: 태수)

#### Backend 담당 범위

- FastAPI 기반 REST API 설계 및 구현
- 분석 파이프라인 오케스트레이션 (Model A / Model B / 번역·TTS 모듈 통합)
- 체크리스트 시스템 설계 및 구현 (백엔드 + 안드 통합 화면)
- Claude / Gemini Vision API 통합 — 가정통신문 정제 + sentence_list 컨트랙트 출력
- 사용자 권한 시스템 — 선생님 ↔ 학부모 분리, 본인 통신문만 접근
- 카드 빌더 / 헤더 슬롯 추출 / 가정통신문 parser 안정화
- 안드로이드 UI 네이티브 재작성 (XML 없이 코드 동적 생성)
- 컨테이너 빌드·배포 자동화 (HF Spaces / NCP Docker)

#### Backend 문제 인식

- 가정통신문 PDF·HWP는 표·자간·줄바꿈이 깨져 raw 추출본만으로 모델이 활용하기 어려움
- 윤정·경이·세종 모듈은 각각 다른 입출력 컨트랙트를 가져 통합 오케스트레이션 계층이 필요함
- 생성형 AI(GPT·Gemini)는 통신문 1건은 분석할 수 있지만, 학부모의 행동 완료 상태를 지속 관리하지 못함
- LLM이 자주 "준비물 → 용품" 같은 임의 어휘 변환을 일으켜 원문 정보가 변형되는 할루시네이션 발생
- 같은 통신문 안에 동일 헤더가 반복되거나 같은 통신문을 재분석할 때, 카드 식별자가 인덱스 기반이면 깨지기 쉬움

#### Backend 적용한 개선 구조

- **레이어드 분석 파이프라인**
  - PDF/HWP 추출 → Claude Vision 정제 → Model A → Model B → 카드 빌더 → 번역 → TTS → 응답 통합
  - 각 단계 timing 로그 부착해 단계별 성능 진단 가능
- **Claude Prompt 엔지니어링 (도메인 특화 + 할루시네이션 차단)**
  - systemInstruction을 가정통신문 도메인에 맞춘 12개 규칙 → 6개로 압축
  - "원문 어구만 사용. 한 단어라도 원문에 없으면 출력 금지" 최우선 원칙
  - 위반 사례 6개를 prompt에 명시 (예: 원문 "준비물" → 출력 "용품" 금지, 원문 "8명" → 출력 "8명 모집" 금지)
  - 출력 직전 self-check 지시 → 학습된 표현으로의 자동 교체 차단
- **sentence_list 컨트랙트**
  - LLM이 13종 RoleHint(target / event_datetime / application_period / submit / fee / supplies / contact 등)로 직접 분류하는 구조 정의
  - pydantic validation 통과한 것만 다음 단계로 전달, 실패 시 룰 기반 fallback
- **체크리스트 시스템**
  - 카테고리(chip) 기반 자체 콤마/슬래시 split — 행동성 카테고리(준비물·제출·비용·건강·안전)만 다중 항목 분리, 정보성(일정·기타)은 미생성
  - stable hash 식별자: `card_id`는 `sha1(header+value)`의 첫 12자, `item_id`는 `sha1(ko+note)`의 첫 12자 — 같은 통신문 재분석에도 ID 동일 → 체크 상태 안정 보존
  - 통합 체크리스트 엔드포인트 `GET /inbox/{parent_id}/checklist` — chip별 그룹화 + 마감일순 평면 리스트 동시 제공
  - 토글 API `POST /checklist/{notice_id}` — 메모리 dict 영속
- **권한 시스템 + 인프라 안전성**
  - 선생님 / 학부모 역할 분리, 본인 통신문만 분석·삭제 가능
  - 데모용 엔드포인트는 환경변수 가드(`ENABLE_DEMO_ENDPOINTS`)로 운영 노출 차단
  - LLM API 키 누락 시 모듈 로드 시점에 경고 로그 + 분석 호출은 안전 fallback
  - 권한 게이트 단위 테스트 추가 (분석/삭제 라우트 7개)

#### Backend — 안드로이드 UI

- **네이티브 재작성**: XML 레이아웃 없이 Java 코드로 모든 화면 동적 생성 — 화면 구조 변경이 코드 한 곳에서 가능
- **선생님 화면**: 통신문 발송 + 파일 업로드 미리보기 (PDF/HWP/이미지)
- **학부모 화면**: 수신함 → 통신문 상세 (원본 PDF 표시) → 분석 결과 카드 (체크리스트·번역·TTS·STT)
- **ChecklistActivity (통합 체크리스트 화면)**: 학부모 계정의 모든 통신문 행동 항목을 5개 탭(준비물 / 제출 / 비용 / 건강·안전 / 마감일순)으로 한 화면에 모음
- **NoticeChecklistDialog (한 통신문 모달)**: 분석 결과 화면에서 현재 통신문만 빠르게 확인하는 하단 슬라이드 모달
- 두 체크리스트 화면 모두 stable hash ID 기반으로 백엔드 영속 dict와 자동 동기화 → 토글 결과가 다음 진입에서도 유지
- **BASE_URL 보안**: 서버 IP를 코드에 하드코딩하지 않고 BuildConfig로 빌드 시점 주입 → 레포 노출 차단

| 항목 | 값 |

| 권한 게이트 단위 테스트 | 7개 (분석/삭제 라우트 + demo 엔드포인트 회귀 방지) |

#### Backend 발표에서 말할 핵심 문장

- 백엔드의 역할은 모델을 호출하는 게 아니라, 학부모가 끝까지 행동할 수 있도록 모델 결과를 묶고 상태를 관리하는 것이었습니다.
- LLM이 임의로 "준비물 → 용품"으로 바꾸지 못하도록, 위반 사례를 prompt에 직접 명시해 학습된 표현 자동 교체를 차단했습니다.
- 체크리스트는 stable hash 식별자로 같은 통신문을 재분석해도 학부모의 체크 상태가 깨지지 않도록 설계했습니다.
- 통합 체크리스트 화면은 한 통신문이 아닌 학부모 계정 전체의 할 일을 chip별로 모아, 생성형 AI가 못 하는 누적 상태 관리를 가능하게 합니다.
- 안드 UI는 XML 레이아웃 없이 코드 동적 생성으로 화면 구조 변경 비용을 줄였습니다.

#### Backend 한계와 향후 개선

- 자녀별 child_id 미적용 (1 parent = 1 child 가정) → 다자녀 시나리오 확장 필요
- 분석 결과 캐시가 시연용 — 다른 사용자 첫 진입 시 콜드 캐시
- 추후 API가 아닌 자체 모델로도 sentence를 API처럼 뽑을 수 있게 실험 중

## 7. 핵심 기능

### 7-1. 체크리스트

- 신청하기 / 제출하기 / 준비하기 / 납부하기 항목으로 분리
- 통신문별 체크리스트: 하나의 통신문만 빠르게 확인
- 학부모 계정 기준 통합 체크리스트: 모든 통신문의 할 일을 한 화면에
- 완료 상태 추적 (체크박스 토글)
- 탭 구분: 준비물 / 제출 / 비용 / 건강·안전 / 마감일순
- **MVP 저장 방식**: 인메모리 (서버 재시작 시 초기화); 실제 서비스는 DB 저장 필요

> 생성형 AI는 설명은 해줄 수 있지만, 학부모가 어떤 항목을 완료했고 무엇이 남았는지 지속적으로 관리하지는 않습니다.

### 7-2. 준비물 이미지·설명

- 대상 품목: 크레파스, 리코더, 클리어 화일, 도화지, 실내화, 물통, 붓, 찰흙, 유성매직, 사인펜
- 제공 내용: 품목명 + 쉬운 설명 + 예시 이미지
- 표시 위치: 메인 번역 화면이 아닌 체크리스트 준비물 항목 상세 내
- 활용 시나리오: 문구점·마트에서 직접 보여주며 구매 가능

> 준비물은 번역만으로 실제 물건을 이해하기 어려운 경우가 있어, 체크리스트 안에서 예시 이미지와 쉬운 설명을 함께 제공합니다.

### 7-3. 미니 달력

- 표시 항목: 신청기간, 운영일시, 제출기한, 결과발표일, 재량휴업일·기념일
- 기간형 이벤트: bar(━━) 표시
- 하루 일정: dot(●) 표시
- 날짜 탭: 이벤트 있는 날짜 터치 시 원문 카드 확인
- 월 내비게이션: ◀ / ▶ 버튼으로 이전·다음 달 이동
- 색상 범례: 신청(파랑) / 행사(초록) / 제출(주황) / 휴업·기념일(빨강)

### 7-4. 문화 접근성 카드

- 대상: 한글날, 어린이날, 재량휴업일, 현장체험학습, 체험활동 등
- 제공 내용
  - 왜 쉬는지 / 어떤 의미인지 설명
  - 학교생활에서 무엇을 확인해야 하는지 안내
  - 아이와 대화해볼 질문 제공
- 단순 단어 번역이 아니라 한국 학교생활 적응 지원 목적

### 7-5. TTS 음성 안내

- 전체 문서를 그대로 읽는 낭독 방식 아님
- 체크리스트 항목, 준비물 설명, 문화 설명처럼 듣고 바로 행동할 수 있는 콘텐츠 중심
- 쉬운 한국어 TTS / 모국어 TTS 선택 가능
- 속도 조절 지원 (0.7× / 1.0× / 1.3×)

## 8. Slot Preservation / info_cards

- **배경**: Model A·B가 todo로 판단하지 않아도 중요한 정보는 버리면 안 됨
- **보존 대상**: 날짜, 시간, 금액, URL, 전화번호, 대상, 장소, 문의처, 신청기간, 운영일시, 결과발표일
- **보호 원칙**: 번역 모델이 임의로 바꾸면 안 되는 사실값은 `__SLOT0__` 토큰으로 치환 후 복원
- **info_cards**: todo로 분류되지 않은 정보성 문장을 별도 카드로 표시 (꼭 확인할 정보 섹션)
- **calendar_events**: 날짜·기간 정보는 달력 이벤트로 별도 가공

> 모델은 문장을 다듬고, slot은 사실값을 지킵니다.

## 9. 번역 안정화 실험 및 정량 지표

### 실험 배경

- NLLB-200 distilled 600M 모델은 범용 모델로 학교 안내문 도메인에 특화되지 않음
- 용어 보존을 위한 여러 방식을 개인 실험 레포(translation-tts-lab)에서 먼저 검증
- 팀 레포에 적용하기 전 어떤 방식이 왜 실패하는지 조건을 기록하는 방식으로 진행

### NLLB glossary injection 방식 비교 실험

| 방식 | 성능 | 실패 원인 및 판단 |
|---|---|---|
| 직접 치환 | 9/17, 53% | NLLB가 치환된 표현과 한국어 조사가 섞인 입력을 안정적으로 보존하지 못함 |
| prefix hint | 1/17, 6% | NLLB가 지시문을 번역 대상 텍스트처럼 처리하는 경향 → hint 효과 없음 |
| slot masking | 0/17, 0% | 준비물 명사를 마스킹하면 문맥이 부족해져 출력이 불안정 |
| glossary + template 구조 | 8문장 17/17 / 20문장 37/37 | 준비물 중심 샘플에서 핵심 용어 보존을 확인 |

**해석**

- 단순 hint 방식은 NLLB가 hint를 번역 대상 텍스트처럼 처리하는 경향이 있어 효과 낮음
- 준비물 명사를 slot masking으로 숨기면 문맥이 부족해져 출력이 불안정해짐
- 따라서 모델에게 전체 문장을 맡기는 대신, 번역할 부분과 보존할 부분을 파이프라인 수준에서 분리
- 준비물·제출물 문장은 NLLB 우회 → glossary 직접 매핑 → 준비물 중심 샘플에서 핵심 용어 보존을 안정화 (제한된 테스트셋 기준)
- 이 실험 결과가 현재 SchoolBridge의 slot preservation / template translation / checklist 연결 구조로 이어짐

### 속도 개선 지표

| 항목 | 개선 전 | 개선 후 | 감소율 |
|---|---|---|---|
| NLLB batch cache 미적용 | cards_nllb 31s | — | — |
| NLLB batch cache 적용 | — | cards_nllb 25s | 약 17% 감소 |

- batch generate: 카드 헤더 14종을 개별 호출(14회) → batch 1회 forward로 전환
- LRU cache(OrderedDict, maxsize=1024): 동일 분석 내 반복 등장 헤더(준비물·비용 등) dedup → NLLB 중복 호출 방지
- 시연 환경 기준 전체 분석 시간 단축 목표(~10s)의 일환

### 초기 품질평가 기록

translation-tts-lab에는 준비물 용어 보존 실험 이전에 수행한 초기 번역 품질평가도 기록되어 있습니다. 입력 방식·용어사전 효과를 초기에 검증한 보조 지표이며, 이후 준비물 용어 보존 실험과는 별개의 평가셋입니다.

| 항목 | 결과 | 비고 |
|---|---|---|
| A/B 입력 단축 | -30.1% | 입력 텍스트 정제에 따른 길이 감소 |
| A/B 속도 향상 | x1.84 | 입력 단축 및 파이프라인 조정 효과 |
| A 품질평가 점수 | 45.8점 | 초기 구조 기준 |
| B 품질평가 점수 | 50.1점 | 구조 개선 후 |
| 용어사전 적용 전 | 39.0점 | glossary 미적용 상태 |
| 용어사전 적용 후 | 89.6점 | glossary 적용 후 |

- 이 수치는 제한된 초기 테스트셋 기준이며, 이후 준비물 용어 보존 실험(17종/20문장)을 별도로 진행
- 용어사전 적용 전후 점수 차이(39.0 → 89.6)는 사전 기반 보정이 학교 도메인에서 효과적임을 확인하는 근거로 활용

### glossary 검수 루프

- 번역 결과에서 학교 용어사전의 권장 표현이 반영되었는지 glossary_hits 필드로 확인
- 권장 용어가 누락되면 missing_term 또는 review_needed로 표시하여 검수 상태를 함께 기록
- 단순히 번역 결과를 생성하는 것이 아니라, 번역 후 검수 상태를 산출물에 함께 남기는 구조
- MVP에서는 slot/template/checklist 구조로 흡수; 향후 번역 품질 관리 기능으로 확장 가능

### 향후 개선: 사전 확장 루프

- 새로운 가정통신문에서 미등록 학교 용어 후보를 추출
- 사람이 검수한 뒤 승인된 표현만 term_glossary.csv에 추가
- 생성형 AI(Gemini 등)는 최종 번역기가 아니라 미등록 용어 초안 추천 보조 도구로 활용 가능
- 사전이 누적될수록 학교 도메인 번역 안정성이 개선되는 구조

- 직접 치환 / prefix hint / slot masking / glossary+template 방식을 동일 평가 세트로 비교
- 실패한 방식의 원인을 기록해 팀 내 적용 방식 결정의 근거로 사용
- 팀 레포에 적용하기 전에 실패 조건을 검증함으로써 파이프라인 안정화에 기여

### OCR Lab

- 가정통신문 사진 입력 경로의 실현 가능성을 사전 검토
- 문서 기울어짐, 표 구조, bbox 순서 오류, 소형 글씨 인식 문제 등 자동화 리스크 확인
- MVP에서는 OCR을 메인 기능에서 제외: 단순화 실패가 아니라, 리스크 있는 경로를 먼저 격리하고 핵심 파이프라인을 안정화하는 기술적 판단
- 향후 확장 시 bbox 기반 highlight와 slot 보정을 연결하는 방향으로 재진입 예정

### 백엔드 연결을 고려한 실험 산출물

translation-tts-lab은 단순 실험 노트가 아니라, 팀 백엔드와 연결 가능한 입출력 구조를 염두에 두고 설계한 실험 레포입니다.

| 산출물 필드 | 용도 |
|---|---|
| source_text | 원문 입력 |
| easy_ko_text | 쉬운 한국어 번역 결과 |
| vi_text | 모국어(베트남어 등) 번역 결과 |
| glossary_hits | 용어사전 적용 여부 확인 |
| quality_label | 품질 검수 상태 (ok / review_needed 등) |
| tts_path | TTS 파일 경로 |

- 팀 레포의 cards/info_cards/checklist/TTS 응답 구조를 설계할 때 참고 가능한 근거 자료로 활용
- 실험 레포는 단순 기록이 아니라 팀 프로젝트 적용 전 검증 공간으로, 재현 가능한 산출물로 관리

### 실험 레포에서 팀 프로젝트로 이어진 적용 포인트

| 실험 결과 | 팀 프로젝트 적용 |
|---|---|
| prefix hint 효과 낮음 | prompt 의존보다 slot/card 구조로 전환 |
| 준비물 slot masking 실패 | 준비물은 checklist + glossary/template로 보존 |
| 날짜/URL은 번역 대상 아님 | slot preservation / formatter로 보호 |
| 용어 누락 발생 | glossary_hits / review_needed 개념을 품질 검수 근거로 활용 |
| 반복 번역 비용 발생 | batch cache / LRU로 중복 번역 감소 |

## 15. PPT에 바로 넣을 핵심 문장

- SchoolBridge는 가정통신문을 번역하는 앱이 아니라, 다문화 학부모가 듣고 이해하고 행동할 수 있게 돕는 음성 접근성 서비스입니다.
- LLM은 최종 기능이 아니라, TTS로 읽어줄 행동 안내 콘텐츠를 만들기 위한 문서 구조화 도구입니다.
- 모델은 문장을 다듬고, slot은 사실값을 지킵니다.
- GPT / Gemini는 설명은 할 수 있지만, 학부모의 완료 상태를 지속적으로 관리하지는 않습니다.
- 체크리스트는 무엇을 해야 하는지, 달력은 언제 해야 하는지, 준비물 이미지는 무엇을 준비해야 하는지, 문화 카드는 왜 그런지 알려줍니다.
- 번역은 이해를 돕고, SchoolBridge는 행동을 돕습니다.
- 발표에서는 핵심 결과만 공유하고, 자세한 번역 안정화 실험 과정은 별도 공개 레포에 정리했습니다.
- 팀 프로젝트에 적용하기 전, NLLB가 학교 안내문 용어를 어디서 오역하는지 실험하고 실패 조건을 기록했습니다.
- 이 실험 결과를 바탕으로 모델이 자유롭게 번역할 부분과 반드시 보존해야 할 slot을 분리했습니다.
- 준비물/제출물은 번역 결과로만 끝내지 않고, 체크리스트와 이미지 설명으로 연결했습니다.
- 세종 파트의 목표는 번역을 예쁘게 만드는 것이 아니라, 학부모가 놓치면 안 되는 정보를 보존하고 TTS로 안내 가능한 구조로 만드는 것이었습니다.
