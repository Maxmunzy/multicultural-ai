# 트러블슈팅 및 제한사항

## 문서 목적

이 문서는 현재 MVP를 구현하면서 마주친 기술적 선택, 구현상 어려움, 그리고 의도적으로 제외한 범위를 정리하기 위한 문서이다.

핵심은 "왜 지금 이 범위로 가는가"를 설명하는 데 있다.

---

| 구분 | 기술 | 담당 |
| --- | --- | --- |

## 설계 결정 사항

### API 응답 표준화

모든 엔드포인트의 응답을 `{ status, data, message }` 형식으로 통일했다.
Android, iOS, 웹 등 어떤 클라이언트에서도 동일한 방식으로 처리 가능하도록 설계했다.

### 텍스트 입력 방식 채택

OCR 대신 텍스트 직접 입력 방식을 선택했다.
MVP 범위에서 핵심 파이프라인(추출 → 분류 → 번역 → TTS)을 먼저 검증하는 것이 우선이기 때문이다.

### 6개 라벨 체계

데이터 수가 약 150개 수준인 상황에서 라벨을 늘리면 클래스당 샘플이 줄어 모델 학습이 불안정해진다.
일정·준비물·제출·비용·건강안전·기타로 단순화하고, 이후 `기타`를 세분화하는 방식을 선택했다.

## 구현 애로 및 제한사항

### 1. 왜 학교 알림에 먼저 집중하는가

문제 정의가 분명하고, 실제 사용자 가치가 바로 드러나며, 데이터 수집과 라벨링 기준을 빠르게 정리할 수 있기 때문이다.
MVP 데모 흐름을 짧은 기간 안에 완성하기에도 적합하다.

### 2. 왜 OCR을 현재 MVP에서 제외했는가

OCR 포함 시 이미지/PDF 처리, 엔진 성능 검증, 인식 오류 대응, 후처리 로직 등이 추가된다.
현재는 텍스트 입력 기반으로 핵심 파이프라인을 먼저 검증하고, OCR은 향후 확장 기능으로 둔다.

### 3. `기타` 라벨의 한계

`기타`는 생활지도·학습·일반공지 성격이 함께 섞일 수 있어 모델이 모호하게 예측할 수 있다.
데이터가 충분히 쌓이면 7개 이상 라벨 체계로 확장하는 방향이 적절하다.

### 4. 번역 품질 한계

초기 MVP에서는 완전한 자연스러움보다 핵심 의미 전달을 우선한다.
학교 맥락 표현이 어색하거나 날짜·비용·제출 표현이 기계적으로 보일 수 있다.
"중요 정보를 이해할 수 있는가"를 우선 평가 기준으로 본다.

### 5. TTS 한계

발음이 부자연스럽거나 한국어·베트남어 간 음성 품질 차이가 있을 수 있다.
긴 문장은 청취 피로도가 높으므로, 데모에서는 짧고 핵심적인 문장 중심으로 구성한다.

### 6. 디바이스 데모 어려움

팀 내 Android 개발 숙련도 차이가 있어 환경 세팅부터 어려움이 예상된다.
복잡한 기능보다 시연 가능한 핵심 UI를 우선하고, 더미 데이터로 먼저 화면을 완성한 뒤 API를 연결하는 방식으로 대응한다.

### 7. GitHub ruleset 이슈

private 저장소에서 ruleset이 적용되지 않아 public으로 변경했다.
이후 PR 기반 머지 방식으로 코드 리뷰를 운영 중이다.

## 현재 MVP의 명확한 한계

포함:
- 텍스트 입력 → 핵심 정보 추출 → 6개 라벨 분류 → 쉬운 한국어 → 베트남어 번역 → TTS 안내

미포함:
- OCR 입력
- 실제 학교 시스템 연동
- 자동 일정 등록
- 자동 답장 전송
- 푸시 알림 자동화

이 범위는 부족해서가 아니라, 핵심 가설 검증을 우선하기 위한 의도적 선택이다.
